# Architecture

Next.js 16 App Router + React 19 + TypeScript. The responsive UI uses custom accessible native controls and Lucide icons. CSS design tokens supply the journal palette and RTL layout. Zod validates API payloads. The local edition needs no credentials. The Pages edition uses a configured free Supabase project and a browser-safe publishable key.

`components/adventure.tsx` owns the local workspace and editors. `lib/model.ts` owns data schemas, financial calculations, dependency impact checks and readiness summaries. `lib/seed.ts` contains planning-only expedition data. `lib/store.ts` creates the version-one SQLite schema idempotently: metadata, expeditions, and individual tables for tasks, destinations, segments, bookings, transport, gear, expenses, dives, training, decisions, options, scenarios and contacts. Records have stable IDs, expedition foreign keys, order and JSON attributes. Foreign keys cascade on expedition replacement. Writes use an immediate transaction and optimistic revision to reject stale clients. The API serializes a workspace snapshot; this is deliberately a personal, modest-scale implementation.

Gear rows carry stable inventory identities shared across expeditions: ownership and equipment edits propagate while packing state remains specific to each expedition. New expeditions reuse existing inventory, and shopping checks for matching owned items across expeditions. A normalized global inventory table should replace this propagation in the production backend. Booking-linked expense rows are payment records. `paid` is the aggregate original-currency payment amount; creating, editing or deleting linked payment records recalculates it. Unlinked expenses add actual spending. Commitments count only Booked/Paid bookings; estimates include all noncancelled bookings and shopping items. Conversion snapshots can be supplied per record; otherwise editable planning rates are used.

The local SQLite file is server-only and ignored by Git. No sensitive document upload or public sharing route exists. The local edition retains a readable copy of records in localStorage after fetch; it is not encrypted. The authenticated cloud edition does not write this record cache. Cold offline navigation is not a full PWA and requires already-cached application assets. Use JSON backups for durable offline reference.

## GitHub Pages and Supabase

The static export renders `components/cloud-workspace.tsx`, which gates the workspace behind Supabase email-link authentication with PKCE. `lib/client-store.ts` selects either the local API or authenticated Supabase RPCs. `supabase/migrations/202610260001_workspaces.sql` stores one JSON workspace per auth user, with owner-only select/insert/update policies and no anonymous table or RPC privileges. Both RPCs are SECURITY INVOKER, keep RLS active, derive ownership from `auth.uid()` and use optimistic revisions. A stale save gets PT409 rather than overwriting another device's edits. Records remain synchronized within that account, not shared publicly.

Cloud client data is validated with the existing Zod schema. SQL constraints enforce the workspace envelope and revision. This is an atomic personal-workspace store, not a normalized collaborative database. Domain tables, private file storage and a full offline vault remain future work.

The API handlers use `route.server.ts` and custom Next page extensions. The Pages target excludes those handlers entirely, exports to `out/` and bundles assets beneath the repository base path. Source data in `.data/` is never part of this export. Browser backup export works through both storage adapters.

`.github/workflows/pages.yml` validates both modes before publishing on `main`. Unit tests run the actual SQL migration in a PGlite PostgreSQL engine and check anonymous denial and isolation between two users. Static browser tests mock Supabase HTTP responses; they do not establish real project connectivity. Live auth, RLS and synchronization must be checked after the user's project is configured. See DEPLOYMENT.md.

## Reservation integration

`lib/reservations.ts` handles destination matching, dated stays and Luxon-based timezone/DST cutoff calculations. `components/reservation-integrations.tsx` exposes connection state and the review queue. Supabase Edge Functions in `supabase/functions/` handle Google OAuth, encrypted refresh tokens, paginated provider-mail scans and self-addressed Gmail reminder delivery. The additional migration isolates token/state/delivery records from browser roles, grants each owner read access to their own inbox and exposes an import RPC only to the service role. Imports lock the workspace, merge provider/reference identity without losing payment fields, and increment the shared revision to reject stale foreground edits. A separately authenticated cron endpoint runs every 30 minutes after operator configuration. Source parsing never supplies an ambiguous deadline. No access or refresh tokens are published in Pages artifacts. See RESERVATIONS.md for activation prerequisites and the distinction between tested code and live Gmail verification.
